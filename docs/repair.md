# Build repair

When the head of a managed GitHub source's target branch fails its GitHub Actions runs, Perpetual repairs it through a pull request. This is the first kind of change [Autopilot](architecture/autopilot.md) makes; merging is decided in [ADR 0002](adr/0002-repairs-merge-after-ci-and-journey-gates.md). This page describes the whole flow: detection, triage, the repair box, the agent, change rules, the pull request and its CI, then the journey gates at the pull request's head, the merge, the Build stage's Autopilot mode and the loop guard, and how the pipeline shows a repair.

## Flow

1. **Detect and triage** (`src/repair/manager.ts`, `src/repair/triage.ts`, no model). The manager polls the target branch's head itself every 60 seconds with an ETag, separately from the gate watcher: a fresh read at start is what makes the baseline rule work, while the gate's heads persist across restarts. A repair opens for a failed head that is not the baseline the controller saw at start, or when a person presses Repair on a failed workflow.
   - The head's runs are read as the connected account whenever it has not passed, a baseline's included, and `GET /api/autopilot` names the branch's own failed runs there as the Build stage's `failed` runs, beside the scanned commit. Build offers Repair on them, with the head's short sha when it is newer than the scanned commit, such as a failed head after a restart or a retry of a newer head's finished repair once the OpenRouter key is added. A request names only a run; the manager reads the head again and refuses a run that is not a failed build of the branch at that head, as well as a head it cannot read again or that moves while the runs are read. The selected source, its managed copy and connected account must still match before a person's repair starts.
   - Credentials and permission failures need a person, read with their case and wording as CI, CLIs and HTTP clients print them: an environment credential not set (`VERCEL_TOKEN is required`), `Input required and not supplied`, `Resource not accessible by integration`, `Permission to … denied to`, `Bad credentials` from GitHub's API or gh, git's `Authentication failed for '…'` and `could not read Username`, gh's `HTTP 401` or `403`, curl's `returned error: 403`, a registry's `401 Unauthorized` or `403 Forbidden`, and npm's `E401`, `E403` and `ENEEDAUTH`. An application's own compile error or failed test about a token, 401, 403 or unauthorized is code, and a passing test's line (`✓`, `✔`, `ok 1`, `PASS`) is never read as an error. Network and deadline failures rerun once. Everything else goes to the agent. An explicit assertion failure, dependency mismatch or compile error outranks network text elsewhere in the same log, including expected timeout output from passing tests, since a rerun cannot fix it. A test failure header without an explicit assertion error can still describe a real network or deadline failure and reruns first; ordinary expected/received output alone does not override that network evidence.
2. **Preconditions.** The agent needs an OpenRouter API key in App Settings and a running Docker. Without either the repair ends as `needs-person` with what to do.
3. **Host copy** (`src/repair/clone.ts`). A fresh clone of the failing commit from the managed source copy's own objects, even a commit behind its HEAD, and from GitHub only when the copy lacks it, made in that copy's turn (`cloneGitHubSourceCommit` in `src/github-source.ts`) under `<dataDir>/repairs/<id>/clone` (0700). The user's own checkout is never read. The copy has no remote, so its config holds no path or credential, and it reads names with their case (`core.ignorecase=false`), as the Linux box does. It is removed after the repair's guest resources are confirmed absent.
4. **Repair box** (`src/repair/box.ts`). The copy is copied into a Docker container, which is the agent's whole workspace, and the commit is checked out again there from the copy's index, since a case-insensitive host such as macOS holds one file for paths that differ only in case. Its image follows the failing job's `actions/setup-*` step (`src/repair/workflow.ts`): `node:<v>-bookworm`, `python:<v>-bookworm`, `golang:<v>-bookworm`, otherwise `buildpack-deps:bookworm`. A version that is not a plain version falls back to the image's default tag, and one the registry has no bookworm tag for, such as `node:14-bookworm`, to the same version on the image's own base (`node:14`), then to `buildpack-deps:bookworm`.
5. **Agent** (`src/repair/agent.ts`, `src/repair/tools.ts`, `src/repair/context.ts`). An AI SDK tool loop on the host, up to four attempts:
   - attempts 1–2 use the Settings model, 3–4 the Escalation model (App Settings; the Settings model until one is saved);
   - each attempt has 100 steps and 15 minutes; the repair has a $2 cost cap summed from OpenRouter's reported cost, plus the provider's own charge it reports for a bring-your-own-key request;
   - an attempt ends done when the model calls `done`, or when it stops calling tools after changing files and every failing step's own script (`bash -e`, pipefail, in its working directory) then passes in the box; weaker models often finish with a message instead of the call (the [bake-off](../bench/repair/reports/README.md): GPT-5 nano never called `done` in this loop, though about two thirds of its changes passed). The pull request's change summary says so;
   - an attempt whose conversation outgrows the model's context window fails, and the next starts afresh; any other request the model rejects needs a person, as do missing credits and a bad key;
   - requests route with OpenRouter `provider.data_collection: deny` and usage accounting on;
   - the prompt holds the failing workflow file, job, step, its `run` command, the redacted log, the rule-based diagnosis and the repository digest twin authoring builds (`repositoryFacts` in `src/environments/evidence.ts`: the top level, CI workflows, deploy and container files, and each package's package manager, lockfiles and scripts, at most 16 KB), all fenced as data; the instructions require reproducing the failure first and never weakening tests or CI;
   - an attempt records `reproduced` only when a `run` before its first change ran one of the failing step's own commands (split at `&&`, `;` and `|`, such as `npm test` in `cd web && CI=1 npm test`) and it exited non-zero; another failing command, or none known, records false.
6. **Change rules** (`src/repair/changes.ts`), on the box's diff before every push, and again on what git staged in the host copy: its own list of paths, and its `--text` diff, so a file git treats as binary, by its content or its attributes, is read and counted too; the change's size, its holds and the pull request's `+N −M` come from that diff:
   - rejected, the attempt fails and the reason is the next attempt's input: added credential text, a path through `.git` or outside the repository, a submodule, anything under `.github/` and deploy configuration the scan found. CI and deploy configuration are rejected rather than held because a pushed branch runs its own workflows with the repository's secrets, and deploy previews build from its configuration, before any person looks;
   - held for a person (recorded as `holds`, which stops the merge), since a person keeps what judges a fix: tests in the usual layouts (folders such as `test/`, `Tests/`, `__mocks__/`, `e2e/`, `testdata/` or `Acme.Tests/`, files such as `add.test.ts`, `login.cy.ts`, `test_add.py`, `conftest.py` or `UserTest.java`); test, lint, type and coverage configuration (such as `jest.config.ts`, `tsconfig.json`, `.eslintrc.json`, `pytest.ini`, `setup.cfg` or `.golangci.yml`), npm's configuration and make files; a manifest whose checks changed, read from both of its versions in the host copy: package.json's `scripts`, `workspaces` and the check tools it configures, pyproject.toml's check tools and task runners, and Cargo.toml's lints; more than 400 changed lines;
   - a credential is a literal (`hasCredential` in `src/redaction.ts`, from the same catalogue `redact` scrubs): a token shape, a URL with a password, or a credential name (any case, such as `GITHUB_TOKEN`, `db_password` or `apiKey`) set to a quoted value, or to an unquoted one outside source code, as in env, YAML or shell files. A reference such as `${{ secrets.X }}`, `$X`, `process.env.X` or `os.environ["X"]` is not one.
7. **Pull request** (`src/repair/github.ts`). The box's diff, byte for byte as git wrote it, is applied to the host copy's index alone, since a case-insensitive worktree such as macOS's cannot hold a case-only rename, and committed as the connected account's GitHub noreply address, then pushed to `perpetual/repair/<short sha>` only, with `--force-with-lease`. The first push leases the commit an earlier repair of the same commit last pushed (recorded as `pushed`), or a branch that does not exist; a branch holding commits Perpetual did not push is a person's, so the repair needs a person and nothing is overwritten. An open pull request of the branch is reused. Git authenticates through `gh auth git-credential` given on its command line, and every gh call runs through `src/github-cli.ts`. A draft pull request opens against the target branch, labelled `perpetual-repair`, with the failure, diagnosis, change, holds, attempts, models and cost, redacted. Later attempts push new commits to the same branch and update the body. A label GitHub refuses is tried again after each later push and when the repair ends; one still missing is named in the repair's reason ("Could not label the pull request perpetual-repair: …").
8. **CI.** The pull request head's workflow runs decide:
   - all passed (skipped ones aside), each workflow whose failure opened the repair among them → the pull request is marked ready for review, the box is removed, and the merge step (10–11) takes over; one GitHub refuses to mark ready goes to the merge step as a draft all the same, so its gates still run and report on its head, and it is marked ready once they were judged, whatever they found; if GitHub refuses again, the fix waits at `ready` ("Mark the pull request ready for review on GitHub."), since a draft never merges;
   - a failure → it is read like the original failure and becomes the next attempt's input;
   - no run within 10 minutes → `ready` with "No workflow ran for the pull request.", still a draft;
   - a failed workflow with no passing run at the head within 10 minutes, such as one that runs only on pushes to the target branch, judged nothing → `ready` with "The failed workflow Release did not run for the pull request.", still a draft, so a person merges it; a head the merge step made by updating the branch is read the same way;
   - runs that end otherwise, such as cancelled → `ready` with that reason, still a draft;
   - attempts or cost exhausted → `failed`, still a draft;
   - a GitHub read that fails, or a connection that cannot be read, is tried again at the next poll, for up to 15 minutes; another connected account ends the repair at once.
9. **Supersede, Stop, restart.** A newer head aborts the repair at once and removes its box, so nothing more is spent, but keeps its open pull request, which may hold a valid fix. A repair in `verifying-gates` is the exception: its merge step verifies a moved target branch itself (11), so a newer head supersedes it, aborting it and closing its pull request, only once that head passes; meanwhile no newer repair opens. A finished repair whose pull request stays open (`ready`, `failed`, `needs-person`, `cancelled`, or `superseded` by a newer head) is superseded, and its pull request closed with a comment, once a newer head passes, or once a newer repair opens its own pull request, so repair pull requests are not left open side by side. A head passes a repair only when each workflow whose failure it fixes passed there, judged by the latest run of each workflow as Build admission reads it: a head where that workflow did not run, such as a commit its paths filter skips, leaves the repair and its pull request as they are. A verified fix, a `ready` repair whose pull request passed CI and is ready for review, stays open beside a newer draft, and after that repair fails, until a newer fix is verified too. Repairs of one commit share its branch and pull request, which closes once for all of them, so a person's second Repair never closes the first's. The pull request is closed before the comment is posted, and a close that fails, such as on a network error, is tried again at each check and after a restart; one GitHub refuses (HTTP 403 or 404) is recorded and not tried again. Whenever the head moves, each such pull request is read once, as the account that opened it, since a merge moves the head whatever its runs do next: one a person merged makes the repair `merged`, with the merge commit that same read names, one a person closed is recorded and left as it is, and a read that fails is tried at the next check. Nothing is posted on a pull request a person merged or closed. Stop aborts the repair and keeps the pull request open; a push already under way is recorded, and no pull request opens after it. Switching the pipeline to another branch of the same repository ends a repair under way of the branch it left at the next check, whatever step it is at, as `needs-person` ("Interrupted when the pipeline switched to dev."), keeping its pull request open, since nothing watches, shows or verifies that branch any more; a rerun follows its own repository. A restart ends an active repair as `needs-person`, or `merged` when its merge was recorded, removes this controller's leftover boxes, and removes every repair's directory under `<dataDir>/repairs`, such as an interrupted repair's host copy or gate checkout.
10. **Journey gates at the pull request head** (`src/repair/merge.ts`, `runRepair` in `src/gate/manager.ts`). The repair is `verifying-gates`. Each Sandbox stage's journey gate runs at the pull request head, in pipeline order, as a repair gate through the gate manager's one-at-a-time queue, after every queued gate of the target branch, one waiting to retry included: the stage's twin is rebuilt at that commit and its reviewed, selected journeys run their approved code, under the same verdict rules, and each gate posts its commit status (`perpetual/<Stage>`) on the pull request head. The gates stop at the first one that does not pass, and have six hours in all; once those run out, the fix waits at `ready` ("The journey gates did not finish in 6 hours."). See [Repair gates](gate.md#repair-gates).
    - The twin is built from the stage's saved twin config, a person's or a generated one, which no branch ever detects again; while the stage's plan is still detected, or it has none yet, from the plan detected from the pull request checkout, as the target branch's gate detects each new commit, so the pull request's own code is judged as its merge would be, never with commands or services the target branch's detection found and the pull request no longer has. That plan is held in memory (`repairPlan` in `src/environments/manager.ts`). A repair gate writes no plan, detection record, draft, generated config or provenance to the stage, since its pull request may never merge: a generated config that fails or builds at the pull request head neither replaces nor clears the stage's draft, so a person's pending draft stays, while a target-branch gate still keeps a generated config's failure as the draft.
    - The checkout is Perpetual's own, `<dataDir>/repairs/<id>/gate-<short sha>` (`checkout` in `src/repair/clone.ts`): fetched from the host copy's objects, or from GitHub through gh's credential helper when only GitHub has the commit (after a branch update), on the repair branch with no remote or credential, and removed once the gates settled. The host copy's own worktree stays at the failing commit, since the fix went to its index alone. The managed source copy, the pipeline's scan and the branch head the page shows never move to a pull request commit.
    - The stage's test workspace is found by pipeline and stage, not by path, so its reviewed cases and approved code run although the checkout's path and commit differ; the run records the pull request head as its source revision.
    - A repair gate never promotes, never supersedes a target-branch gate or is superseded by one, and never makes Production Ready; the stage keeps showing its target-branch gate. It does replace the stage's twin with the pull request head's until the next gate or a person rebuilds it. That twin names its repair, so the stage card shows it, with a PR head badge whose hint is the repair branch and the head's short sha, rather than as behind the scanned commit.
    - A Stop, a supersede or the six hours running out end a queued repair gate at once as superseded, even one the queue has just chosen, which then never starts; a gate at work reaches its verdict first, and the next stage's gate then ends as superseded without running. A queued repair gate whose pipeline is no longer active, or whose stage was removed, ends as needs release. A controller restart ends a repair gate at work or queued as needs release ("Interrupted by a controller restart.") and reports that on the head, and its repair needs a person.
    - Release on GitHub's required check: a person may release a repair gate that needs release through the gate API (`/api/gate/release` with the pull request head), which reports success on the head and promotes nothing.
11. **Merge.** Perpetual squash-merges the pull request through GitHub's REST merge, naming the verified head (`sha`) so GitHub refuses one that moved, only when all of these hold:
    - every gate passed at the head; one that failed, needs release or was released leaves the fix `ready` with the reason ("Beta needs release: No reviewed journeys."), so a stage without reviewed journeys never merges by itself;
    - no change rule held it ("Held for a person: The change touches tests.");
    - the Build stage's Autopilot mode is `Autopilot`, not `Ask first` (12);
    - the pull request is open, not a draft, still merges the repair branch into the target branch, and its head is still the verified one, read before its checks and again after them; one a person merged meanwhile makes the repair `merged` with GitHub's merge commit;
    - every check run on the head completed as success, neutral or skipped, and every commit status on it succeeded, the gates' own included; one still pending is read every 15 seconds for up to 10 minutes, and more than ten pages of either leaves it for a person;
    - the target branch has not moved since the pull request's base: its head, read from GitHub last, just before the write, is compared with the pull request head. No GitHub API guards the base of a merge, so the target branch can still move in the moment between that read and the merge; the merge commit's parent then shows it, and the repair is `merged` with that reason ("main moved to abc1234 during the merge."), while the target branch's push gate judges the merge commit as it does every push. When it moved, GitHub merges it into the repair branch (update-branch, naming the verified head); only GitHub's merge commit, whose parents are the verified head and the target branch head Perpetual compared, is recorded as pushed and goes through CI and the gates again, and any other new head leaves the fix ready ("The pull request changed after verification."); at most two updates per repair ("The target branch kept moving."), and one GitHub refuses, such as for a conflict, leaves the fix ready.
    A merge records the merge commit at once (`merged`), even when the repair stopped meanwhile. Anything else leaves the repair `ready` with its reason, and after a merge the ordinary push gate runs on the target branch. A repository without a Sandbox stage merges on CI alone, and its managed source follows the merge commit at the gate watcher's next poll.
12. **Autopilot mode.** The Build stage's Autopilot Badge opens a menu with **Merge changes** (`merge`, the default) and **Ask before merging** (`ask`), kept per pipeline in `<dataDir>/repairs/state.json` (`POST /api/autopilot/mode {repoPath, stageId, mode}`). In `ask`, a repair stops at `ready` once CI and its gates ran ("Auto-merge is off."); the mode is read just before a branch update and the merge, with nothing awaited between it and the write, so choosing Ask before merging while a repair verifies prevents its merge.
13. **Loop guard.** A head that is the merge commit of a repair's pull request, merged by Perpetual or by a person, and that fails again opens no repair by itself: it is `needs-person` ("The merge of repair #7 failed again."), and a person may still start Repair on it. A person's merge is known by the merge commit (`merge_commit_sha`) of the same read that found the pull request merged, when the head moved or when Perpetual closed it as superseded; a merged repair whose read named none is read again at each check until one does. Until the guard knows every merge the connected account could have made at the head, a failing head opens no repair by itself and is read again at the next check: every pull request the account opened for its repository that may still be open must have been read at that head, including one being closed as superseded, one whose close GitHub refused and one whose repair ended, such as at ready or by Stop, after the head moved while its gates were at work, and every merged repair's merge commit must be known. After 10 checks that could not judge the head, the guard gives up on what it waited for: the head is `needs-person` ("Could not tell whether this is the merge of repair #7."), and no later head waits for that pull request until the controller restarts. A merge Perpetual never saw is not guarded.

## What the box may do

- Run anything inside itself as root.
- Reach public addresses only, through its egress proxy (`src/repair/egress.ts`). The box sits alone on an internal Docker network with no route to the host, the local network or the internet, whose bridge has no address on the engine's host (`com.docker.network.bridge.inhibit_ipv4`), so a host service listening on every address is not reachable through it either. The proxy is a separate container on the default bridge (`node:22-bookworm-slim`, read-only, no capabilities, user `node`, 256 MB) that joins the box's network as `proxy` and forwards CONNECT tunnels and `http://` requests only to public addresses: a destination that is, or resolves to, a loopback, private, link-local, shared, reserved or multicast address is refused, and the address it checked is the one it connects to. So `host.docker.internal` and every listener behind it (the controller, the twins) and the local network are out of reach.
- It has no host mount, no Docker socket, no GitHub token, no OpenRouter key and no host environment; only `CI=true`, `DEBIAN_FRONTEND=noninteractive`, `GIT_TERMINAL_PROMPT=0`, and the proxy settings package managers, git, curl, JVMs and Node read (`HTTP(S)_PROXY`, `NO_PROXY` for localhost, `JAVA_TOOL_OPTIONS`, `NODE_USE_ENV_PROXY`). The docker CLI itself runs with the engine variables and the shell basics only (`dockerEngineEnvironment` in `src/process.ts`).
- It runs with `--security-opt no-new-privileges`, all capabilities dropped except `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `FSETID`, `SETUID`, `SETGID` and `KILL`, 4 GB of memory without swap, 2 CPUs and 1024 processes.
- Docker Desktop's storage has no per-container quota, so while the box works its written layer and Docker's free space are read every 15 seconds, and every minute while no command runs, since a process a command left running in the background may still write while the model thinks or CI runs; once it wrote more than 20 GB, or Docker has less than 2 GB free, the box is removed and the repair needs a person with that reason.
- The box, its proxy and its network are labelled `perpetual.owner=repair`, `perpetual.repair=<id>` and `perpetual.data=<hash of the data directory>`. Leftovers are removed by those labels only, before each new box and after a restart.
- The agent reaches it only through its tools: `list`, `read` and `grep` in `/workspace` with capped output; `edit` and `write` in `/workspace`, never `.git`; `run` with a timeout of at most 900 seconds; and `done`. A path is checked as text on the host and by its real path in the box, so a link cannot lead out.
- Tool replies use the shared redaction catalogue before local formatting and clipping. `read` and `grep` first read each complete file, at most 256 KiB, and redact it on the host before selecting lines. `grep` retains native extended-regex matching, order and its 100-match limit; each matched file is read once and its original matching lines must still agree. Changed files, escaped paths, incomplete file reads and redaction that changes line counts are refused rather than shown with inaccurate evidence. A capture the box already truncated is withheld with an instruction to narrow the command, retaining its actual exit code, timeout and truncation state. Catalogue redaction recognizes credential shapes present in an observation; an arbitrary shell command that extracts or encodes a value can remove that context.
- Only the host copy pushes, and only the repair branch.

## Cleanup and recovery

The manager records cleanup ownership before allocating a repair workspace. Cleanup is separate from the repair outcome: a known merge and its SHA stay merged while cleanup is pending or failed. The repair box confirms that its labelled container, proxy and network are absent before the host workspace is removed. A failed observation or deletion keeps ownership and the workspace, preserves the business reason alongside a redacted cleanup reason, and holds new repairs.

A person's retry of a finished repair waits for its final save, then checks the source, connected account, head and failed run again. Stopped or superseded work still ending, and pending or failed resource cleanup, continue to hold new repairs.

Later checks and restart recovery retry cleanup only; they never repeat model work, pushes or merges. A startup sweep of the controller's owner/data labels finishes before any new agent starts, including for older terminal history whose clone was already deleted. Only history that may have made a box needs it: a repair at work or holding cleanup, or one that recorded an attempt, a push, a pull request or a merge, and any repair directory left behind. A controller whose repairs ended at triage, or whose agent step could not start, such as on a machine without Docker, does not contact Docker. A sweep that fails holds new repairs and is shown as the cleanup hold, without marking repairs that hold no cleanup, while heads, reruns and pull requests are still followed. Once cleanup starts, the box accepts no more commands, including when deletion needs retrying.

## Interface

A repair is a change of the Build stage, shown as [Autopilot](pipeline-ui.md#autopilot) shows every change: the Badge names the work under way (`Fixing build`, or `Rerunning build` for a network or deadline failure), the Border Beam runs while it works, and the change's row on the rail lists five steps, **Read the failure**, **Diagnose**, **Change**, **Verify** and **Merge**, each with the facts the controller recorded: the failed run and commit, the diagnosis, the attempt and model, the pull request, CI and each journey gate's verdict, and the merge commit. A rerun that passed lists two steps and ends `Passed`. **Clean up** appears while cleanup is under way or waiting after failure; it does not change the recorded merge outcome.

- **Repair** is a Button on a failed workflow row of the GitHub Actions card, for the watched head's own failed run of that workflow, with the head's short commit when it is newer than the scanned one. It is offered while the head has no repair under way and no fix waiting with its pull request; a repair that ended without one, such as one that needed a person, may start again.
- **Stop** is a Button on the change under way; its pull request stays open.
- The Badge menu's **Merge changes** and **Ask before merging** are the Build stage's Autopilot mode (12).
- **Escalation model**, a second model Select in App Settings, chooses the model attempts 3 and 4 use; a strong coding model the catalog lists is preselected, else the Settings model.

How a repair reads as a change (`src/repair/view.ts`):

| Repair | Change | Step |
| --- | --- | --- |
| `triaging`, `rerunning`, `repairing`, `verifying-ci`, `verifying-gates` | `Running` | the step at work is active |
| `merged` | `Merged` | every step done |
| `flaky` | `Passed` | Read the failure and Diagnose done |
| `ready` | `Needs review` | Merge waits, with the reason |
| `failed` | `Not merged` | Change or Verify failed, with the reason |
| `needs-person`, `cancelled`, `superseded` | `Needs review` with an open pull request, else `Not merged` | the step it stopped at waits, with the reason |

## API

| Method and route | Input |
| --- | --- |
| `GET /api/autopilot` | `repoPath`; returns the contract's `AutopilotView` (`contract/autopilot.ts`): the Build stage's mode, its changes newest first, and the watched head's `failed` runs a person may repair. `GET /api/state` carries the same view as `autopilot`. |
| `POST /api/autopilot/mode` | `repoPath`, `stageId` (Build), `mode` (`merge` or `ask`) |
| `POST /api/autopilot/repair` | `repoPath`, `stageId` (Build), `runId`: a failed run of the watched head; replies `202` |
| `POST /api/autopilot/stop` | `repoPath`, `stageId` (Build), `id`: the change under way |

Another source answers `409`; a stage other than Build, an unknown mode or a run that is not a failed build of the branch at its head answers `400`.
