# Twins

A twin is a Sandbox stage's application environment: the product's actual code and the services it depends on, running as a local Docker Compose project whose app URLs a [business journey](journeys.md) can target. The controller owns each twin's lifecycle and each journey's verdict. The design is recorded in [Twins and the journey gate](architecture/twins-and-gate.md).

A twin does not clone a production account, copy production data or create Vercel, Railway or other provider resources. Each dependency comes from one service file in `src/twin/services/`: the vendor's official simulation or local mode when one exists, [`vercel-labs/emulate`](https://github.com/vercel-labs/emulate) only when none does, and never a hand-written mock. A service whose test input is missing is **blocked**; nothing substitutes for it.

A running twin, a healthy app and a passed business journey are separate states. An app that answers HTTP does not prove that its authentication, payments or database are configured correctly.

The current app runner supplies a Node image. Before creating services or starting paid configuration authoring, automatic environment creation checks the source snapshot for Python web entrypoints corroborated by their project's runtime dependencies (Django WSGI/ASGI, FastAPI and Flask). Such an app stops creation with its source evidence and an instruction to use an existing application URL for browser tests; a runnable Node site in the same repository cannot silently replace it. A person's explicitly saved twin config selects the apps instead, so a supported product may coexist with a runnable tutorial in another language. Generated configs do not count as that selection, even when reused by a gate. This check does not implement Python execution or establish complete runtime coverage. It does not rank folders, remove documentation apps, or treat development-only dependencies, optional extras and quoted examples as products. Existing-URL browser tests remain available independently of twin creation.

Requirements: Docker Desktop with Compose. A twin's containers reach its services through `host.docker.internal` on ports published on the host's loopback, which Docker Desktop routes; on a native Linux engine they cannot, so twins do not work there (see [Source and data boundaries](#source-and-data-boundaries)). The first twin pulls images and installs app dependencies, which can take several minutes.

## From Pipeline to a twin

1. Add a Sandbox stage such as Beta and confirm the source repository and branch. The stage's twin config and environments belong to that repository and stage.
2. Detection proposes a twin config, its apps and services, the first time the stage is opened; the stage's **Services** list shows its services. When it finds no app, an OpenRouter API key in Settings lets an agent write the config on Create.
3. Choose **Create Beta environment** (the button names the stage). A stage has one twin: an earlier one that still holds resources, such as one whose containers stopped, is deleted first, after any health check of it finishes. A deletion that fails, or an earlier twin still in use, such as by a journey run, stops the creation with its error. The controller copies a filtered source snapshot, records ownership, runs each service's setup, creates test accounts, runs the shared install and the fixtures, then runs `docker compose up --wait`. The environment records how long each step took. It becomes Ready when the twin is up, every app answers, and a test account exists where a service can create one; blocked services are listed with the inputs they are missing. While the stage's config is still the detected one and App Settings has an OpenRouter model, an agent writes the config first, and the controller verifies it by building this twin; see [Generated twin config](#generated-twin-config).
4. Run reviewed journeys against an app URL. A newly ready environment may prepare journey drafts when a model, the browser runtime and an unambiguous application URL are available; drafts are never approved or run automatically.
5. Delete the environment when finished. Deletion runs `docker compose down --volumes` and each service's teardown, removes containers that interrupted one-shot commands left, and confirms that none of the twin's volumes remain. A cleanup failure stays visible and is never reported as a successful deletion.

The environment inspector contains the stage's **Integration tests** and **Runs**. Within it, environment progress shows the current step, recorded timings, failed attempts and expandable redacted logs. **Stop** cancels an in-progress creation and waits for its processes and owned resources to be cleaned up; cleanup failures remain visible and keep ownership for a deletion retry. The stage card's **Services** list, marked `Generated` when an agent wrote the config, shows each twin service with its provenance (`Actual`, `Official sandbox` or `Emulate`) and status (`Ready`, `Blocked` or `Not started`); **Connect** on a blocked service asks for its missing inputs; for Stripe it also offers to [create a sandbox](#a-stripe-sandbox-without-an-account). A created sandbox's row shows its expiry and a **Claim** link.

## The twin config

One config per Sandbox stage, stored as data. Catalogued provider credentials, including signing keys a service owns but only supplies with an option, cannot be replaced by randomly generated internal secrets. Command fixtures receive their selected service’s variables; aliases and required account arguments must be set explicitly from the repository script. For a Next.js app with an API, Supabase and Stripe:

```json
{
  "services": {
    "supabase": { "users": [{ "id": "owner", "email": "owner@example.test" }] },
    "stripe": { "webhook": "{{apps.api.url}}/stripe/webhook" },
    "mailpit": {}
  },
  "install": { "directory": ".", "command": "pnpm install --frozen-lockfile" },
  "apps": {
    "web": { "directory": "web", "build": "pnpm build", "start": "pnpm start", "port": 3000,
             "env": { "NEXT_PUBLIC_API_URL": "{{apps.api.publicUrl}}",
                      "NEXT_PUBLIC_SUPABASE_URL": "{{services.supabase.publicUrl.api}}" } },
    "api": { "directory": "api", "start": "pnpm start", "port": 3000 }
  },
  "fixtures": [{ "service": "supabase", "sql": "seed/twin.sql" }]
}
```

- `services` maps a service id to its options. Unknown services are rejected when the config is saved.
- An app runs its `build` and then its `start` command on a Node image with Corepack enabled (the bundled version when available, otherwise pinned `corepack@0.34.7`, compatible with Node 25 and newer): `node:<major>-bookworm-slim` for the config's optional `node` major. Detection takes it from the repository root's `.nvmrc`, `.node-version` or `package.json` (`volta.node`, `devEngines.runtime`, `engines.node`). A version or range gets the newest maintained major it admits, an LTS (24, then 22) before the current release (26), so `>=18` runs on 24 and `>=25` or `26.1.0` on 26; one that admits none of them gets the newest released major it admits, a former LTS before an odd major, so `>=20 <22` runs on 20 and only a range such as `^25` on 25, and one above every release gets the first major it admits. Without one, it is the current LTS, `node:24-bookworm-slim`. The install and command fixtures run on the same image. An app must listen on `port` (also given as `PORT`, which its `env` cannot change) on all interfaces, and no app may be named `source`, the step that copies the source. Directories are relative to the source root.
- An app variable with the name of a service's standard variable, such as `DATABASE_URL` or `STRIPE_SECRET_KEY`, is filled automatically. Other names map explicitly with `{{<service>.<VARIABLE>}}`, `{{apps.<id>.url}}`, or `{{services.<id>.url.<port>}}` for a service's address on one of its named ports; `{{services.<service>.<VARIABLE>}}`, with an upper-case name, is the same variable as `{{<service>.<VARIABLE>}}`. When two services provide the same variable, the app must map it explicitly.
- Browser requests, including URLs compiled into frontend code, use `{{apps.<id>.publicUrl}}` or `{{services.<id>.publicUrl.<port>}}`. These select the allocated loopback address and also work in that app's build and server through its TCP relays; `url` keeps the container-reachable address. Choose by where the source consumes the value, including browser redirects and allowed origins, not by a variable's prefix. Existing saved plans and service outputs are never silently rewritten; update browser mappings explicitly. Real external vendor URLs stay unchanged.
- Callback routes may derive their origin from the framework's request URL instead of an app's base-URL variable. The config author reads those routes and configures the installed framework's supported public hostname/port separately from its `0.0.0.0` listening socket and `PORT`, including any supported loopback-hostname normalization. `PORT` is the configured container port, not the browser port allocated by `publicUrl`; a framework may derive its request URL from startup settings even when the incoming Host header has the public address. Browser cookies distinguish loopback IPs from `localhost`: the framework's origin and browser-origin environment values must use the same hostname before application modules load, retaining their allocated ports. The audit follows entry, sign-in, vendor return and protected readback, including origins compiled during the build; a launcher changes neither the entry link nor an already built bundle. A supported auth flow must keep or establish its session on the return hostname. Prefer repository configuration and commands; when necessary, a thin `start` command may use the framework's official server interface and delegate every request to the unchanged application. Its public address comes from an `env` mapping to `publicUrl`, with no fixed allocated port. This is per-repository configuration data, never a framework-wide override, replacement server, response rewrite or permission change. An app answering HTTP still does not establish that its checkout or other business callback works; those need real journey acceptance.
- Service setup runs in the order that `{{<service>.<VARIABLE>}}` placeholders in service options imply. Addresses are allocated before any setup, so they impose no order.
- Unknown placeholders, circular references, and a variable or named port the referenced service does not declare are rejected when the config is saved. A service declares its standard variables, those its options add and its named ports; a repository file's variables are known only at setup and checked then, but one an option decides, such as the Stripe webhook's secret, is judged at save. Placeholders go in service options and app `env` only: a command (`build`, `start`, `install.command`, a fixture's `command`) that holds one is rejected, since a command reads the variables `env` fills as `$VARIABLE`, and so is a fixture's `query`, inline SQL that reads no twin value: braces it stores are written apart, as `'{' || '{name}}'` stores `{{name}}`.
- A service option named `env` is an environment, like an app's: a variable that references a blocked service is left out. Any other option that references a blocked service blocks that service too. An app variable that references a blocked service is left out.
- `install` (optional) runs once, after services are ready and before fixtures and apps, because command fixtures such as seed scripts need workspace dependencies.
- A fixture has exactly one of `sql` (a repository file), `query` (inline SQL kept with the config) or `command`. SQL fixtures run `psql` against the service's `DATABASE_URL`, so one on a service that does not provide it is refused when the config is saved. Fixtures run after services are ready and before apps start.

A plan saved by an earlier version, with services that had install and start commands, is replaced by a fresh detection.

### Detection

Detection reads repository evidence only; it never runs repository code.

- **Apps**: scanned Next.js, Vite, Express, Fastify and Hono packages with a `dev` or `start` script, and any other package with a `start` script. Dependencies install where the nearest lockfile is (`pnpm`, `yarn` or `npm`). A `start` script runs after the package's `build` script. Vite and Next.js commands get host and port flags. Scripts that reach a cloud account or publish (`vercel dev`, `railway run`, `deploy`, `semantic-release`, …) are not proposed; the word in a flag (`--release`), a folder (`dist/release/`) or Prisma's `migrate deploy` does not count. When two or more apps share one workspace lockfile, detection proposes one `install` step and removes that install from their builds.
- **Services**: each service file's `detect` rules, matched against repository paths, dependency names in `package.json`, `requirements*.txt` and `pyproject.toml`, and variable names in example env files such as `.env.example`. Values are never read, and actual `.env` files are not evidence, nor are the files of tests, docs and tooling folders (examples, fixtures, samples, evals, benchmarks, playgrounds and stories) as the generated config's evidence classes them. A service that already runs another (Supabase runs its own PostgreSQL) replaces it. A service's `detect.options` gives the options its proposal starts with, so a detected config passes the service's own checks: `emulate` runs the vendors whose packages or variables the repository shows.

## Generated twin config

Detection finds which services and apps a repository has, not the wiring its product needs: app variables mapped to service variables, test accounts, seed data, the secrets it requires. So when a person creates the environment of a stage whose config is still detected, or whose generated config has failed to build since, and App Settings has an OpenRouter model, an agent writes the config and the controller verifies it by building the real twin. AI authors the config as data; the gate rebuilds from the saved config with no model. Every build of a saved config, a person's or a generated one, is ready only when the same check passes: every app answers its address with a status below 500, and a test account exists when a service in it can create one. A rebuild that fails it fails its environment, so a gate's twin that is not ready gives no verdict; a generated config keeps that failure as its draft.

- The agent is OpenCode by default, the harness that [journey code generation](journeys.md#generating-code) runs (see [Author harnesses](#author-harnesses)), in a private workspace: `repo/` holds an author-only copy of the environment's source snapshot, `twin.json` the current draft, `feedback.md` why the previous attempt failed, `EVIDENCE.md` the repository's evidence, and `TWIN.md` the config format, these rules, the tools' limits and a catalog of every service generated from `src/twin/services/`. `opencode.json` names `TWIN.md` and `EVIDENCE.md` as its `instructions`, so both are in context from the first step. It may read, glob, grep and list files and edit `twin.json`: no shell, no network, no other write; `lsp`, `task`, `webfetch`, `websearch` and `skill` stay denied. For a GPT model OpenCode edits with `apply_patch`, which can move `twin.json` anywhere it may reach: every folder outside the project is denied, the project's git metadata is beside it, and an attempt that changed any other file in the project, `.git` included, is refused.
- Both author harnesses receive complete text with catalogue-recognized credentials and known supplied secrets removed before excerpts, line selection or clipping, preserving source line numbers. A supplied value shorter than eight characters, such as a local model server's placeholder key, is no credential: the author's copy, evidence and feedback leave it in place, while the twin's own logs and errors, which feedback quotes, still hide one of four characters or more. The author copy omits links, non-regular entries and credential-bearing paths, and replaces binary contents with an omission notice. The twin executes the separate, unchanged source snapshot. Stored service inputs are read without provisioning before the first attempt; all values seen during that creation remain protected across input changes and retries, and are never written into the author's instructions or environment.
- Author process output is captured within a fixed limit and protected before retaining its tail. If a stream exceeds that limit, its text is withheld; the actual exit, timeout, cancellation and cleanup result still determines the outcome.
- The editable `twin.json` keeps its exact text and valid placeholders. A draft or authored result containing a recognized token, private key, literal URL password or known supplied secret is refused; use the config's service references for those values. Ordinary literal configuration remains supported. Refusal never turns redaction markers into a runnable config or replaces the saved draft.
- `EVIDENCE.md` holds variable names, paths and quoted setup commands, with recognized and supplied credentials removed before formatting. The authors read it as formatted: token shapes and supplied values are removed from it again, but its own `NAME: file:line` lines are never taken for credential assignments. Nothing of the repository runs to compute it (`src/environments/evidence.ts`, with the setup files' readers in `src/environments/setup-configs.ts`). The controller caches repository facts from the snapshot, rereading them when supplied secrets change so protection still precedes clipping. Its files are those git tracks in the checkout (`git ls-files`, with git's file system monitor off) that the snapshot keeps, in git's order, at most the first 50,000; when git cannot list them (no git metadata, nothing tracked, or git failing, which it names), a walk of the snapshot 16 folders deep. The snapshot's privacy exclusions hold either way: no `.env` file, no folder such as `secrets/` or `credentials/`.
- Each attempt's `EVIDENCE.md` starts with the work list, **Unwired variables**, computed from the `twin.json` that attempt starts from: for each app, the variable names its runtime code reads, and the code of the workspace packages its `package.json` depends on, less the standard variables (`provides`) of the services configured, `PORT` and the names its `env` maps. Each name has the first `file:line` that reads it, the example env file that lists it, and whether a build-time public prefix (`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `EXPO_PUBLIC_`, `PUBLIC_`, `NUXT_`) puts it in a front end's bundle. The list then names every Supabase-style edge function, `<project>/functions/<name>`, in any project of the repository: whether the `supabase` service serves it (its `functions` option, from `functions.directory` or the project's own `functions` folder) and the names its code reads that `functions.env` does not map, less the `SUPABASE_` names the edge runtime gives every function; a folder whose name starts with `_` is code the functions share. An app may call a function kept in another project than the database's, so an unserved function is listed with what it reads, and feedback names the unserved functions that read variables.
- Then CI and deploy evidence: each GitHub workflow's jobs, with their runner, services (image, ports), working directory, variable names, setup actions' versions, the `uses` names and `run` lines (200 characters each) of their steps, and the secrets and variables they reference; deploy manifests (`railway.toml|json`, `vercel.json`, `Procfile`, `fly.toml`, `render.yaml`, `netlify.toml`, `nixpacks.toml`, `railpack.json`) with their build and start commands, directories and variable names; Dockerfiles (`FROM`, `WORKDIR`, `ARG` and `ENV` names, `EXPOSE`, `CMD`, `ENTRYPOINT`); dev containers (image or build, features, forwarded ports, setup commands, `containerEnv` and `remoteEnv` names); and `turbo.json` (tasks and their variables).
- **URL operations** follows CI and deploy evidence: at most 50 runtime source lines matching `new URL(` or `redirect(`, with file and line locations and an omitted-line count. The same bounded source-read pass collects them without source contents or URL values; docs, scripts, tests and tooling are left out. These are unclassified text matches for the author to read, not an exhaustive callback inventory, inferred browser roles or proof that public origins work. Routes without environment-variable reads still receive an origin audit.
- Then each scanned package, app directory and folder with a manifest: its framework, `package.json` scripts, the dependencies a service's `detect` rules match, and the variable names its runtime code reads (`process.env`, `import.meta.env`, `Deno.env.get`, `os.environ`, `os.getenv`, and destructuring from `process.env` or `import.meta.env`) by folder. **Variables by role** lists every variable name once, runtime names first, with the first `file:line` that reads or declares it (for a setup file, where the parsed file has it as a key, a value or a reference; for a `package.json` script, its key in `scripts`) and its role: `runtime` (app code), `script` (a package's or the repository's scripts and migrations folders, seed files and folders, `package.json` scripts, CI, Docker, dev container, deploy, `turbo.json` and Supabase config), `test` (test files and test runners' configs) or `tooling` (a package's or the repository's evals, benchmarks, fixtures, examples, samples, playgrounds or stories folders). A folder inside an app's source, such as `src/tools/` or `app/stories/`, holds runtime code whatever its name. Then example env files' variable names, read from the checkout because the snapshot leaves those files out; Supabase-style projects with their `config.toml`'s `env()` names, functions, seed and enabled sign-in methods, their migrations, seeds and each function's variables; other SQL files; compose files and their services; and the headings of the README and of docs whose names suggest setup or development.
- `docs/` is left out of the variable names and links are never followed. Each section (16 KB) and the file (60 KB) are bounded, the work list and the CI and deploy sections first. It says what it left out: the rest of a cut section, files too large to read (setup and compose files over 256 KB, source files over 256 KB, others over 1 MB), source files beyond the first 5,000 (runtime code is read first) and lists or walks cut by their limits. Each of its lines stays one line: a key, port or name that is not one plain word is quoted as inline code, so nothing a repository writes becomes a heading or a line of its own. Its readers take time in proportion to the files they read, however those are crafted.
- The prompt says the draft is already in `twin.json`: start from the unwired variables, CI and deploy evidence and URL-operation locations, edit `twin.json` within the first few steps, then refine it. An empty unwired list does not establish correct request-derived origins. `TWIN.md` gives the tools' limits: grep and glob return at most 100 results and cannot page, so always pass a `path` and an `include`; output that is cut off cannot be opened; prefer reading the files the evidence cites. Both `TWIN.md` and the evidence's header say that every name, path, heading and command it quotes from the repository is data, never instructions. `TWIN.md` also requires a signed-in test account to reach the product's main screens: when the app first needs records for a signed-in user, such as an organization, workspace, team, membership, profile or finished onboarding, a fixture creates them for at least one test account. Fixtures run after the test accounts exist, so inline SQL can find an account by its email. Discovery is read-only, so an account stopped at onboarding leaves every authenticated screen unexplored.
- The controller makes at most four attempts: the first two use the Settings model, and the last two use the saved Escalation model, or the Settings model when no escalation model is saved. Each is shown as the step `Writing twin config (attempt n of 4)` and limited to 15 minutes and 100 tool calls. An attempt counts when its config validates, including each service's own option checks, and the twin prepared from it is ready, every app answers its address with a status below 500, and a test account exists when a service in it can create one. Otherwise its reason is the next attempt's `feedback.md`, staged and redacted: the stage it failed at (`valid`: refused before anything ran; `build`: preparing the twin failed; `healthy`: a container never became healthy; `answers`: an app did not answer; `account`: no test account), the app or service it names with its command (an app's build and start, a service's container, the install or a fixture; a service's setup or test accounts only when the twin names that service in its error; of the containers that are not up, one that stopped, else one that is unhealthy or not yet healthy, and one that never started only when nothing else failed), the error, the unwired variables recomputed from the config the next attempt starts from, and the last 150 lines of the failed containers' logs. The failed twin is torn down first.
- An attempt that runs out of time is not the end of generation. Once its processes have stopped, a `twin.json` that differs from the attempt's draft and parses as JSON is its output, validated and prepared like any other; otherwise the attempt failed, and its feedback asks the next attempt to edit `twin.json` first, starting from the unwired variables. At the step limit OpenCode 1.18.32 disables the agent's tools and has it reply once, which ends the run normally, so the `twin.json` it wrote is checked like any finished attempt's; an attempt that ends, there or otherwise, without ever writing `twin.json` fails, and its feedback asks the same. Writing the draft back unchanged counts as writing it. An agent that cannot start, stops, or whose processes could not be confirmed stopped ends generation, as does cancellation.
- A config that counts becomes the stage's config with its provenance (`generatedAt`, `harness`, the successful attempt’s `model`, `attempts`), which `GET /api/environments` returns with it, and the stage's Services show `Generated`. After four failed attempts the environment fails with `Writing the twin config failed after 4 attempts:` and the first line of the last failure; the last config and its feedback stay as the stage's draft, which the next creation starts from. When the agent's processes could not be confirmed stopped, the environment stays `cleanup_failed` until it is deleted.
- Each completed author's config that fails validation or preparation is saved with its failure as a draft before the next attempt; Stop discards only the unfinished author's edits, and a restart keeps the draft without starting paid work.
- The environment's error is always a short sentence, such as `The twin config author stopped.`. The end of the agent's output, from each attempt that ran out of time or stopped, goes only to the environment's logs (`POST /api/environments/logs`), redacted, ahead of the twin's own.
- A generated config that later fails to build, in a person's creation or a gate's rebuild, becomes the stage's draft with its failure, staged as an attempt's is under the heading `The saved twin config`, when the failure names a part of the config: it is refused, or it names an app, service, the install or a fixture. The stage keeps the config itself. The next creation a person starts generates from that draft instead of the detected skeleton; a creation that builds the generated config again drops the failure. A failure that names no part of it, such as Docker being unavailable, leaves no draft, so the next creation builds the config again rather than paying for a new one.
- A person's saved config is never generated again, and a generated one only after it failed as above. Opening a page, restarting the controller and a gate's rebuild never generate; a gate uses the saved config, or the detected one when there is none.

### Author harnesses

`PERPETUAL_TWIN_AUTHOR` chooses what runs each attempt: `opencode`, the default, or `loop`, Perpetual's own author (`src/twin/author-loop.ts`), an AI SDK tool loop on OpenRouter that the controller runs as its own Node.js process in the same workspace, so the workspace, the check that only `twin.json` changed, cancellation, the time limit and the logs are the same. Its tools are its only permissions: `list`, `read` and `grep` inside the project (an absolute path, a parent path or a link out is refused; a search follows no link, returns at most 100 lines and stops after 5 seconds, its `include` glob matched within that time as one expression, never expanded), `write_config`, which validates a config as the controller does and writes `twin.json` only when it is valid, returning the error or the unwired variables recomputed from `facts.json`, which the controller writes beside the project, at once, and `done`. It runs no command and reaches no network but the model's, through the proxy that `HTTPS_PROXY` names when one does, and the key is only in its environment and never in its output. It stops at 100 steps, at `done` or after 15 minutes; a model that has written no valid config by its twelfth step must write then, or its attempt ends, and a third write in a row that fails with the same error asks it to change approach. Its output is one line per tool call and the tokens and OpenRouter cost of every answer, one that broke a forced write included; a provider's refusal stops generation with `Error:` as OpenCode's does, while a request longer than the model's context window, which the history it keeps can grow into, ends the attempt with what it wrote, as its step limit does. Provenance names it `perpetual-loop@<AI SDK version>`.


## Services

| Service | Provenance | What runs |
| --- | --- | --- |
| `postgres`, `redis`, `mongodb`, `mailpit` | Actual | The official images, with generated passwords. Mailpit accepts any SMTP credentials. |
| `llm` | Actual | A real model. By default the App Settings OpenRouter key and model; with `source: app`, the app's own development values, supplied as the service's inputs. |
| `secrets` | Actual | Internal secrets several apps share, such as a webhook signing secret, generated per twin from `names` ending in `SECRET`, `KEY`, `TOKEN` or `PASSWORD`. Rebuilding rotates them. |
| `supabase` | Official sandbox | Local Supabase through Supabase CLI 2.118.0, including the [Edge Runtime bind-mount fix](https://github.com/supabase/cli/pull/6505). The CLI is an exact dependency of Perpetual: `package-lock.json` locks it, its platform binary and its own dependencies with their integrity hashes, setup installs them, and a twin runs that installed release, never one it downloads or one a `SUPABASE_CLI_BINARY_OVERRIDE` names. Database credentials come from `supabase status`. Edge functions, test users and a token issuer on the twin's address are supported. Each `env()` value of the project's `config.toml`, and every `SUPABASE_` variable but the CLI's own image registry, home and telemetry settings, stays unset, whatever the controller's environment holds. |
| `stripe` | Official sandbox | **Create sandbox** generates test credentials from an email, without an existing Stripe account or key; an existing account's test secret key and publishable key can also be connected. `stripe fixtures` and `stripe listen` supply fixtures and forward the listed events to the twin. |
| `trigger-dev` | Official sandbox | One self-hosted Trigger.dev instance per machine; each twin gets its own project and a `trigger dev` worker running the repository's tasks with an exact CLI version. The instance's secrets stay with the data directory that set it up and its volumes carry their id, so another data directory never takes it over, even one that kept the secrets of an instance since removed; volumes created before they carried an id belong to a data directory that holds secrets. Deleting a twin starts a stopped instance, unchanged, to delete the twin's project. The instance runs no Electric or object store, so Realtime run subscriptions and offloaded large payloads do not work. |
| `emulate` | Emulate | Only vendors with no official simulation: GitHub, Google, AWS, Linear, Vercel API and Apple. It refuses vendors that have an official test mode, such as Stripe, Twilio, Clerk, Okta, Auth0, Resend and Slack. |

Adding a service means adding one file to `src/twin/services/` and one import to `src/twin/registry.ts`. The file declares how the service is detected, the test inputs it needs (and optionally how to create them), its setup, containers, standard variables, optional test accounts and teardown, its entry in the config author's catalog (`describe`) and the checks of its options (`validate`). Product-specific settings belong in the twin config, never in a service.

Supabase CLI 2.118.0 passes an explicit import map outside [the context Edge Runtime reads](https://github.com/supabase/edge-runtime/blob/v1.76.2/crates/base/src/runtime/mod.rs#L501-L504). For a legacy map, Perpetual adds a function-local `deno.json` pointing to the same map only in the isolated project's mounted `functions` tree, preserving the map, its scopes and the TOML. Existing `deno.json` and `deno.jsonc` files, including visible ancestor configs, are kept. Map and entrypoint paths must remain inside that copy without symbolic links. Conflicting maps in a shared entrypoint directory, wrappers that would change another function's inherited config, and legacy entrypoints outside the mounted tree need explicit function-local Deno configuration. Remove this compatibility bridge once a pinned official CLI passes both the legacy-map and native-Deno Docker acceptance cases without it.

### Test inputs

A service may declare inputs, such as a Stripe test secret key, created on request or supplied by the user. They are test credentials only: validated by pattern, stored once per machine in `<data>/twin-inputs.json` (mode 0600), reused across twins and never sent to the browser. Views say only whether each input is set. Any additional account setup required by the application's journeys remains the user's responsibility in the sandbox's Dashboard.

Input storage uses a private directory (mode 0700), guarded reads and atomic replacement of each file. Both `twin-inputs.json` and `twin-provisions.json` are limited to 1 MiB each; links, non-files and oversized files are refused. A save checks both resulting file sizes before replacing either, so exceeding a limit preserves the previous values and provision record.

A service may instead create its inputs on the user's action. The values are stored with the other inputs, and a record of the provision (the inputs it ran with, its expiry and any claim link) is kept apart in `<data>/twin-provisions.json` (mode 0600). One provisioning runs per service at a time; another provision or a manual save during it gets 409. Values whose provision has expired (its expiry date is today or earlier, UTC) are never used, so the service is blocked and nothing substitutes for it. Creating a twin, a gate's rebuild included, reads the existing credentials without recreating a sandbox or sending its stored email. An expired service stays blocked until the user chooses **Create sandbox** or supplies valid test keys through **Use keys**. Saving the service's own keys ends the provision and replaces every value it provided. Views and deletions never create or renew anything. The claim link appears only in the local Services view, never in logs, errors, gate reasons or commit statuses, and keys appear in no view.

### A Stripe sandbox without an account

Stripe journeys need no existing Stripe account or pasted key. In a stage's **Services**, **Connect** → **Create sandbox** runs `stripe sandbox create` in the pinned Stripe CLI image with the email entered there, pre-filled from `git config --global user.email`, and saves the generated test credentials. It runs only on that explicit action, because the email is sent to Stripe. The result is [Stripe's official hosted sandbox](https://docs.stripe.com/sandboxes), so the dependency order is unchanged.

- The sandbox expires after 7 days unless it is claimed. Perpetual never recreates it automatically: its keys remain in use until expiry, then Stripe is **Blocked** until the user connects it again. **Create sandbox** creates a new account; Dashboard setup from the old account does not transfer.
- Its limited `rkcs_test_` key covers `stripe listen`, fixtures, Checkout, subscriptions, the billing portal and webhooks. Test clocks and the balance API need a claimed sandbox's full keys: choose **Claim**, then **Connect** → **Use keys** and enter them, which replaces the sandbox's keys and removes its expiry record.
- **Use keys** takes the test secret key and the publishable key of the same account. Both are required, so Stripe is **Blocked** until both are saved and provides `STRIPE_PUBLISHABLE_KEY` whenever it is not; a saved secret key alone leaves **Connect** asking for the publishable key.
- Each attempt uses a fresh, empty CLI config in a private temporary directory, with a 90-second timeout and telemetry off. Anything but the expected result fails with one fixed message, `Stripe could not create a sandbox. Try again later, or enter test keys.`; the CLI's output holds keys and is never shown.

The `stripe` service's `fixtures` option is a `stripe fixtures` file in the repository or, when the repository has none, the document itself in the twin config: named requests to the Stripe API's `/v1/` paths (get or post, with params) and an `env` map of upper-case names to their ids, such as `"STRIPE_PRICE_PRO_MONTHLY": "${pro_monthly:id}"`. It runs at setup against the sandbox only, and each name its `env` map lists is a variable the service provides.

### Test accounts

A service can create test accounts once its containers run, before the install and fixtures. Supabase creates its `users` through its local Auth admin API. Each account gets a generated password, stored only in the twin's private state (mode 0600) and redacted from its output; views list the id, label and username. Rebuilding a twin replaces the passwords. A run with no account choice uses the first account, so automatic gate runs need no input.

Auth account failures identify a stable hashed account reference, the method and path template, elapsed milliseconds and the last observed phase: not sent, awaiting response headers, reading response body or response received. They distinguish the existing 20-second request deadline, cancellation, HTTP failure and transport failure. A failed dispatched POST or PUT has an unknown write outcome, even after response headers arrived: it may already have committed. Perpetual neither increases that deadline nor retries that mutation. Email, password, remote user ID, headers, keys, request bodies and raw responses stay out of the summary. Generated passwords and account emails are registered for redaction before the request starts; older twins' saved account values are also hidden from logs.

Before a failed twin is torn down, including between config-generation attempts, the environment record saves diagnostic evidence through its existing private state store. This includes setup and Compose output and Supabase's CLI-owned database, enabled Auth and gateway logs. Vendor containers are inspected by exact declared name and their project label is verified; logs use the resulting immutable container ID. Missing containers, wrong labels and unreadable logs produce an explicit unavailable entry. Evidence collection and storage failures do not replace the original preparation error or stop cleanup. Unconfirmed cleanup keeps resource ownership and twin state.

Each collection reads at most 200 lines per command and eight vendor containers, sharing a 20-second Docker-read budget (plus up to five seconds to stop an owned CLI process). Each command refuses more than 1 MiB of raw output and discards it rather than retaining a partial secret. Redaction precedes clipping: setup and Compose each keep at most 32,000 bytes and each vendor container 8,000 bytes. The latest combined environment evidence is capped at 128 KiB, with at most 32 environments' evidence retained for seven days; saves, startup and log reads enforce retention, and explicit successful deletion removes it. Expiry changes no resource ownership or result. Logs help investigate local sandbox failures; they do not change readiness or business-journey verdicts, and a subsequent successful attempt does not establish the cause of an earlier timeout. Keep production credentials and customer data out of twins.

## Source and data boundaries

Creation copies a working-tree snapshot; it does not modify the original checkout or mount it into the twin. A one-shot container copies the snapshot into the twin's own `workspace` volume, and the install, apps and command fixtures run from that volume, because writing dependencies and build output through a host bind mount is several times slower on Docker Desktop.

Package managers keep downloads, and Corepack the package managers it installs, in a package cache that the install, apps and command fixtures use. The twins of one repository share its cache, `perpetual-package-cache-<digest>`, named from a digest of the repository's identity: a connected GitHub repository with its Root Directory, or a local checkout's path. Deleting a twin keeps that cache for the repository's next twin, and another repository's twins never mount it. A [repair gate](gate.md#repair-gates)'s twin builds a pull request head no person has reviewed: its cache is its own, an empty `package-cache` volume of its Compose project that is removed with the twin, so nothing that code writes reaches a later twin. A twin created by an earlier version mounts the machine-wide `perpetual-package-cache` volume until it is rebuilt or deleted; no other twin mounts it, and `docker volume rm perpetual-package-cache` removes it once none does.

The snapshot excludes `.env` files, package-manager and credential files that can hold tokens (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pypirc`, `.netrc`) at every depth, private-key files, local provider state, dependency and build caches and local database files. In a git checkout it also leaves out every file git ignores, through the `.gitignore` files of the repository and of each repository or submodule inside it, and the user's excludes, whatever the file is called; when git cannot list them, creation stops and says why. Local agent configuration directories (`.codex`, `.agents`, `.claude`) and instruction files (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `CLAUDE.local.md`) are excluded at every depth. JavaScript, TypeScript and Python source modules named `credentials` or `secret(s)` are kept, as are `build`, `dist` and `coverage` directories beneath `src`. Symbolic links are not source inputs. Limits: 20,000 files, 256 MiB in total and 32 MiB per file. Filename exclusions do not prove that application source contains no embedded credentials; keep production secrets and customer exports out of the repository and the twin config.

Internal `url` placeholders use `http://host.docker.internal:<port>`, published on 127.0.0.1 only. The exception is the `supabase` service: the Supabase CLI starts its own local stack and publishes its ports itself, and Perpetual does not limit them to loopback. Explicit `publicUrl` placeholders, app links and local browser targets use `http://127.0.0.1:<port>` so a host browser can also reach APIs referenced by a frontend. For each app, a supervisor in its existing Node image binds only the public ports that app explicitly references, before its build and start commands. It relays raw TCP to those same allocated ports through `host.docker.internal`, so a variable shared by browser, SSR and middleware keeps one origin. It adds no host mount or Docker socket and changes no API response. Internal placeholders, service-provided defaults and literal URLs do not create relays. A bind conflict prevents the app from starting; a listener failure stops it. App exit or container stop closes listeners and connections and terminates the app's process group, with forced termination after two seconds if needed. The supervisor confirms its direct child has been reaped and its process group has terminated before exiting; an observed Linux zombie or dead process counts as terminated. Cleanup that cannot be confirmed within four seconds fails explicitly.

This host-gateway path is verified on Docker Desktop, including official local Supabase Auth and app-to-app requests. Native Linux Docker is not supported: a host-gateway address does not reach a port published only on the host's loopback. Perpetual does not widen published ports to work around that limitation.

Views of older owned twins expose the loopback app URL without rewriting their saved URLs or container configuration; their browser-consumed env mappings still need an explicit update and rebuild. Perpetual's browser retains its `host.docker.internal` mapping for older plans, which does not make those addresses work in other host browsers. Host ports are allocated upward from 43100 in blocks of 48 per twin, excluding every configured app's listening port to leave room for its relays. There is no outbound network block: application code, install scripts and page resources can reach networks, and a hardcoded production endpoint is not intercepted.

## Controller API

Every request is scoped to an explicit `repoPath` and Sandbox `stageId`: in the query string for GET, in the JSON body for POST. An environment ID alone does not select another source or stage.

| Method and route | Input |
| --- | --- |
| `GET /api/environments` | Returns the stage's environments and twin config (`plan`), with its `provenance` when an agent wrote it. |
| `POST /api/environments/plan` | `plan`: a twin config. |
| `POST /api/environments/create` | Uses the stage's config; a detected one may be generated first. A config that is not generated needs at least one app. The stage's earlier twins that still hold resources are deleted first. |
| `POST /api/environments/cancel` | `id`; returns 202 after requesting Stop. The environment stays busy until process and resource cleanup finishes. |
| `POST /api/environments/destroy` | `id` |
| `POST /api/environments/logs` | `id`; recent twin logs, after a failed generation preceded by the end of the twin config author's output, with secrets redacted. |
| `GET /api/twin/services` | The stage's twin services, their provenance and missing inputs. |
| `GET`, `PUT /api/twin/inputs` | Which inputs are set, and each provision's expiry and claim link; `PUT` takes `{service, inputs}`. |
| `POST /api/twin/inputs/provision` | `{service, inputs}`: creates the service's inputs, such as a Stripe sandbox from `{email}`. |
| `POST /api/stages/remove` | Confirms removal of the Sandbox stage and all its owned environments. |
| `GET /api/stages/removal` | Removal progress; reading never starts or retries a removal. |

An environment reports `services` (`id`, `title`, `fidelity`, `status`, `missing`), `apps` (`id`, `url`) and test `accounts` without passwords. Creation and deletion take time: read the current state rather than treating an accepted request as completion.

## Shared use and recovery

Browser journeys, health checks and environment deletion share one reservation per environment. A browser target belongs to an owned environment through its app origins, including loopback aliases and `host.docker.internal`, across stage boundaries. An unrelated external URL needs no twin. A busy environment skips its health check. Independent environments can run at the same time.

Confirmed stage removal persists its source and stage before cleanup. Closing the page or selecting another source does not cancel it. The stage is removed only after every owned environment is cleaned up; a cleanup failure keeps the stage and its reservation for a retry. Startup resumes an accepted unfinished removal, but never silently retries a failed cleanup or replays discovery or tests.

Controller shutdown stops new admissions, cancels the commands preparing a twin and cleans it up after their processes stop, cancels owned browser workers, and saves final results and ownership. Ready environments remain. Forced termination is different: an interrupted environment operation or browser run leaves the affected environment blocked for cleanup on restart, because application work may still be active. Unrelated ready environments stay usable.

Only one controller may open a given data directory; ownership is acquired before recovery and released after shutdown. This is a same-host guard, not coordination across shared network storage.

Browser process cleanup holds its reservation until owned descendant processes exit. Unconfirmed cleanup quarantines the environment, which then needs explicit deletion before reuse.

The health monitor reads the twin's containers every 30 seconds, including Supabase's CLI-owned database, gateway and enabled Auth. The gateway remains required when Supabase's Data API is disabled. These reads inspect exact container names and verify the owned project label; healthy app containers cannot hide a stopped dependency, healthy external services cannot replace missing Compose containers, and missing or unreadable observations cannot establish readiness. A stopped or unhealthy container, or a Compose service whose container is gone, fails the environment at once; other check errors must repeat first. An environment its health monitor failed is rechecked on the same cadence and becomes Ready again when its containers are healthy. Recovery does not recreate the twin or regenerate tests, and it does not apply to creation failures, interrupted operations, cleanup failures or destroyed environments.

## Runtime storage

Perpetual-generated Compose containers (apps, service dependencies, install and source copy) and the shared Trigger.dev stack use Docker's `json-file` driver with rotation at 10 MiB per file and at most three files per container. Recent output remains available to diagnostic log reads. A new or rebuilt twin receives the policy; the shared Trigger.dev stack applies it on its next setup, recreating changed containers while keeping its named data volumes and instance secrets. Restarting an existing container alone does not change its log driver configuration. This bounds Docker stdout/stderr logs, not application-internal files, database data or containers created independently by a vendor CLI.

Each environment keeps its source snapshot in `<data>/environments/<id>/source` and its twin in `<data>/environments/<id>/twin/`: `compose.yaml`, `.env` (mode 0600, holding every value; `compose.yaml` only references it) and `twin.json`. Deletion removes both. While its config is generated, the agent's workspaces are under `<data>/environments/<id>/authoring/`, removed when generation ends. At most eight environments exist at once.

Twin and shared-port storage directories are private (mode 0700); existing directories have their permissions repaired. A twin's state and the shared service port map use guarded reads: symbolic links, non-files, malformed state and oversized files are refused. Files are replaced atomically at mode 0600, and a failed replacement removes its temporary file. Parent path aliases keep the same configured paths and resource owner labels.

`twin.json` has a 32 MiB read budget. A service may return teardown information after creating resources, so preparation saves that information in full before checking the budget. An oversized result fails preparation and keeps the complete state for manual recovery; it cannot be automatically loaded or cleaned up, including after restart. Refused state never counts as absent or successfully destroyed, and its files remain. Resolve the oversized state and its owned resources before retrying.

`<data>/twin-services/ports.json` is limited to 1 MiB. A reservation that would exceed that limit leaves the previous map intact. Host port allocation reads every existing twin's saved block and the shared map in one module-wide queue shared by the process's runtime instances, and records its reservation before releasing the queue. The controller's same-host ownership guard prevents another controller from opening that data directory; the queue itself does not coordinate processes. Invalid existing reservations block allocation until recovered. Service setup runs outside that queue so it can reserve a shared-instance port itself.

An environment created before Compose twins ran its app in a Cua guest. It loads as Failed with the step Retired, and deleting it removes that guest.

Service and app images are pinned by tag, not by digest, so a twin is not a fully reproducible supply-chain lock.
